## 二、问题 1：工作流能否继续改进？

**结论：骨架健康，不需要动核心机制。** 「一次一单元、90 分钟中断守卫、实测回写、只 commit 不 push」这套队列状态机已被实战验证，改进空间集中在以下 6 点（按建议优先级排序）：

### 2.1 程序轨尚未复用美术轨的队列模式（M0 启动时做）

美术轨的最大资产不是图，是这套被验证的异步长任务模式。M0 启动时建议照抄：建 `docs/程序生产日志.md`，把 M0–M6 拆成带验收标准的派发单元，沿用「磁盘即状态 + 一次一单元 + 实测回写」。开发计划目前只有里程碑叙事，没有状态机文件。

### 2.2 player_walk 是队列外的隐藏重做候选（一句话成本，防遗忘）

时间线（git 与日志交叉证实）：`player_walk` 8 帧（模仿模式）产于「围巾基准修正」（side 围巾改挂前身 + 新增 three_quarter 基准）**之前**；修正条目明确写了「后续动画重做时围巾统一为绕颈+贴身垂尾基准」。但 U 队列（U9–U14）中没有该事项——它只存在于计划外任务表的措辞里。建议在队列或计划外表显式登记一条「player_walk 按新围巾基准重做（待用户确认是否需要）」，避免跨机器续跑时遗忘。

### 2.3 加最小 CI：兑现「资产可复现」承诺的自动化验证（高价值，纯增量）

仓库经 GitHub 在 Windows/macOS 双机间同步（tools README 明示）。目前「脚本重跑 → 与在盘资产零像素差异」只在目录整理时**手工**做过一次（98/98 一致）。建议加一个最小 GitHub Action（Python + Pillow 即可，零新增依赖）：

1. 跑全部 `gen_*.py` 输出到临时目录；
2. `pixcli diff <临时目录> assets/` 验证零差异；
3. 按资产分组跑 `pixcli check`（exit 0 门禁）。

这把「可复现」从口头约定变成每次 push 的机械验证，同时防双机漂移、防误改资产。

### 2.4 `pixcli check` 自动按资产分组（工具改进，消除已知坑）

「一次 check 只喂一个资产的帧组，整目录混检会假阳性」目前靠 SKILL.md 列坑 + 人守纪律（生产日志踩过）。check 可按文件名 stem 前缀自动聚合帧组再逐组检查，坑从纪律变成默认正确。约几十行 Python。

### 2.5 把 U8 沉淀的「连通域检查」固化为程序化门禁

U8 审查沉淀的「主体 1 + 碎影 N、碎影不与主体粘连」目前是审查员的手工方法。它可程序化（连通域计数 + 拓扑判定），加入 `check.py` 后模仿类/碎影类资产多一道免费门禁。

### 2.6 数值双源漂移的预防（程序轨启动前定规则）

`游戏设计.md` 自我定位「数值唯一事实源」，M2+ 实现后数值必然同时存在于文档与代码两处。建议提前定规则：数值在代码中收敛为单一常量模块（如 `src/data/balance.ts`），文档标注「实现口径以该文件为准，本文档为设计快照」——或反向。demo 规模手工双写也可接受，但规则要先把口径定死，否则调参阶段（M5「回写文档」）必出漂移。

### 明确不建议改的

- **队列串行「勿跳序」**：理论上 U13/U14 与 U9–U12 无依赖可并行，但 token 额度与审查带宽是实际瓶颈，且并行会破坏「磁盘即状态」的单写者假设。demo 规模不值得。
- **效率模式的上下文成本**：≈90% token 是输入（上下文重读），批量派发摊薄已是最大杠杆且已用足，无进一步明显优化空间。

## 三、问题 2：是否有冗余设计？

**结论：核心架构（三源文档 + 门禁 + 模式分层）无冗余，模式分层有实测成本数据支撑。** 发现 3 处真实冗余/坏味道、2 处「看似冗余实则有意」：

### 3.1 真实冗余

| # | 发现 | 证据 | 建议 |
|---|---|---|---|
| R1 | **`gen_player.py` 的 `draw_run`/`RUN` 是死代码，且其逻辑被复制而非复用** | `main()` 已不输出 run（文件头注明「run 6 帧组已被 walk 替代，部件函数保留供 walk 复用」）；但 `gen_player_walk.py:89` 自述「与 gen_player.draw_run 完全相同的部件顺序与画法，仅姿势数据不同」——实际只 import 了 `gp.HIP_F_RUN` 常量，画法是另写的一份 | 二选一：让 walk 真正 import `draw_run`，或删除死代码。改后用 `pixcli diff` 验证产物字节级不变 |
| R2 | **共享基元寄居在单元脚本里：`shade_mask`/`rows_to_inside` 定义于 `gen_batch1_extras.py`，被 U5/U6/U8 三个脚本当库 import**；而定位为「风格基准库」的 `style_kit.py` 反而不含它们——同属「轮廓偏移法」的明暗实现分居两处 | import 关系经源码 grep 证实（u5/u6/u8 各 1 处 `from gen_batch1_extras import rows_to_inside, shade_mask`） | 下沉到 `style_kit.py`（或独立 `shading.py`），`gen_batch1_extras` 回归纯单元脚本；改后同样跑 diff 验证 |
| R3 | **6 份 agent 定义重复嵌入同一套基准条文**：尺寸档位/调色板/命名/目录在 artist 两份中逐字重复，在 reviewer 两份与 imitator 两份中以压缩形式重写；基准变更需人工同步 7 处（含 AGENTS.md）。实证成本：目录整理一次就同步了 4 份 agent 定义 + 11 个 gen 脚本 | 六份定义全文已通读比对 | 抽单源 `.zcode/agents/_pixel-conventions.md`，各定义头部改为「先读该文件」。代价：每次派发多读一个小文件；收益：消除漂移风险。可与下一次基准变更合并做，不必专门动 |

### 3.2 看似冗余、实为有意（不建议动）

- **调色板三格式**（`dungeon_palette.json/.txt/.png`）：分别服务工具/人读/预览，U1 还为 txt 一致性修过 P2——三格式是三受众，不是冗余。
- **`assets/template/` 整包入库**（几十个动作目录 + `.aseprite` 源）：目前只用了 Walk，俯视角两向游戏大概率用不到 Katana/Punch/Climb 等侧视动作。但 imitator 定义把模仿定为「任意源 × 任意目标」的通用能力，保留全包有其价值；包体仅百 KB 级，不伤根本。若求仓库洁净可裁剪至已用目录，属可选而非建议。
- **效率/全量/模仿三套 agent 对**：表面是 6 份相似文档，实际是拿「全量 ≈ 效率 6 倍成本」的实测数据换来的分层定价，impostor 对则有独立的双参照审查职责。保留。
