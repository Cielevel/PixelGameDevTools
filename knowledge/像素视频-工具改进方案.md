## 0. 结论

「调参调不出稳定结果」的根因不是参数没找对，而是**缺判据**——现在的反馈只有肉眼看闪不闪。三处改动：

| # | 改动 | 落点 | 作用 | 实测效果 |
|---|------|------|------|----------|
| **A** | 时间维滤波 | `video.py` / `video-studio.html` | 压掉帧间颜色抖动 | 核心静止格变色率 33.2% / 49.1% → **9.6% / 21.5%** |
| **B** | 稳定性读数 | `video-studio.html` | 把判据变成数字 | 调参从「感觉」变「看数」 |
| **C** | 导出端 + 门禁 | `video.py` / `video-studio.html` / `pixcli` | 产出引擎可消费形态 + 拦截退化 | 规格见 `跨引擎交付契约.md` |

A 与 B 是同一件事的两半：**B 给判据、A 给手段**。只做 A 是盲调，只做 B 是知道差但没办法。建议同批做。

## 1. 判据定义（先定，否则 A/B 无法验收）

- **静态格**：片段全程 `alpha > 0` 的格（各帧不透明格的交集）。
- **核心静态格**：静态格中 8 邻域也属于静态格的子集（排除轮廓边缘与描边抖动）。
- **帧间变色率**：相邻帧对中颜色发生变化的格数 / (格数 × 相邻帧对数)；分别对静态格、核心静态格统计。
- **单格平均色数**：每个静态格在片段中出现过的不同颜色数，取平均。

**为什么这样定义**：运动本身必然改变颜色，所以只统计静止格——把闪烁从运动里分离出来。现有 `pixcli anim` 的「相邻 diff 率」是全局像素差，跑步时天然很高，被运动淹没，**不能用来定位闪烁**；本指标可以。

**基线（2026-09-08 实测：12fps 抽帧、48 帧、64×64、跨帧共享 16 色板）**

| 素材 | 静态格 / 核心 | 变色率 全部 / 核心 | 单格平均色数 |
|------|---------------|--------------------|--------------|
| dog_walk（绿幕） | 1179 / 973 | 38.6% / **33.2%** | 4.17 |
| Pixel_art_walking（蓝幕） | 785 / 629 | 48.8% / **49.1%** | 4.78 |
| ↑ 加时间中值(5) | 同左 | 12.0% / **9.6%** | 2.67 |
| ↑ 加时间中值(5)（蓝幕） | 同左 | 21.3% / **21.5%** | 3.35 |

**目标（暂定门禁）**：核心静态格变色率 **≤ 5%**；单格平均色数 **≤ 3.0**；静态格数 **< 50 时报「样本不足」**，不判通过（全屏运动片段不适用该指标）。

## 2. 改动 A：时间维滤波

### 算法（2026-09-08 修订：加运动感知门）

逐像素沿时间轴取中值（降采样后 1 像素 = 1 逻辑格）。对输出帧 `i`、像素 `(x,y)`：

0. **运动感知门**（实测补丁）：当前帧与**任一相邻帧**（`i±1`）同态（同为透明，或同为不透明且
   **各通道差 ≤ TOL=24**）→ **保留当前值**。持续 ≥2 帧的变化是真实运动/换色，不该被中值抹平；
   容差是为了让运动边缘的**过渡色**也留下（精确匹配会把过渡色判为「与前后帧都不同」而拉回旧色 = 拖影）；
1. 否则按窗口 `[i - w//2, i + w//2]`，**首尾收缩**（不 pad、不循环——避免引入首尾帧的假色）；
2. 窗口内 `alpha > 0` 的帧的 RGB **逐通道取中值** → `med`；
3. 窗口内 alpha 中值 `≥128` → 不透明，否则透明；
4. `med` 按 **OKLab 最近色**映射到跨帧共享色板（复用 `standardize.map_with_palette`）。

**为什么必须加门**：纯中值在运动区会把 ±2 帧的旧颜色拖到当前位置——实测 12fps/64×64 下
**63% 的运动像素被冻结**（= 明显拖影），且 w=5 时 2 帧残影达 **2.70%** 像素。

### 为什么放在「共享色板量化」之前

中值结果通常不是色板上的颜色。**先滤波再映射**：最终色数不增、仍受 ≤16 色约束。若在量化之后滤波，会引入色板外新色，破坏色数门禁。alpha 必须与颜色同步处理，否则出现半透明残留。

### 插入点（已核对当前代码）

- **`pixel-toolkit/video.py`**：第 **373 行之前**——即 `if not keyed:` 背景透明化块（367–372）之后、`# 跨帧共享色板量化`（374）之前。此处 `outs` 已是目标尺寸的 RGBA 列表，正是所需输入。
- **`pixel-toolkit/video-studio.html`**：`buildLibrary()` 内第 **984 行之后**、第 **986 行 `// ③ 跨帧共享色板量化 + 描边`** 之前。此处 `raw64` 是全部帧的 `{width,height,data}` 数组。

    """沿时间轴逐像素取中值；palette=[(rgb,lab)] 时映射回共享色板。

### 参数与代价

- `w`（窗口帧数；12fps 下 ≈ 0.25s）：越大越稳、运动拖影越重。**默认值经二次修订改为 0（关），平滑默认由「时间众数稳定」承担——见下方「CLI 暴露」**。
  **注意窗口按帧数计**：同样 `w=5` 在 12fps 覆盖 ±0.17s、在 6fps 覆盖 ±0.33s——采样帧率越低拖影越久。
- 容差 `TOL=24`（各通道，仅运动感知门用）：越大越不拖影、但保留的帧间变化也越多（读数变差）。
- **只对静止区域有效**；运动区域的颜色抖动本指标不测、该算法也不修。
- **副作用（2026-09-08 实测）**：逐像素中值不与邻域耦合，少数帧会因邻域像素 alpha 中值先变透明而留下 **1 个孤立不透明像素**（dog_walk 50 帧中 7 帧各 1 处，`pixcli check` 记 P2——信息级、非门禁）。视频派生产物本就是参考素材（契约 §6），暂不做后处理清除。
- **不修**：网格相位漂移（见 §6）、抠像边缘残留（那是 key 的问题，`e564405` 已处理一部分）。

### CLI 暴露

**2026-09-08 二次修订：默认改由「时间众数稳定」承担**（实测它在闪烁与拖影两个维度都更好）：

- `pixcli video-std --stabilize N`（量化**后**逐像素取窗口众数、平局保留当前帧；`0`=关，**默认 3**）；
  对应 `video-studio.html` 的「后处理 → 时间稳定」（默认 3 帧众数）。
- `pixcli video-std --temporal N`（量化**前**中值；`0`=关，**默认 0**，保留为可选手段；旧素材复现显式传 `0`）。
- 两者口径分别在 `standardize.temporal_mode_frames` / `temporal_median_frames` 与
  `video-studio.html` 的 `temporalStabilize` / `temporalMedianFrames`，前端口径对拍逐字节校验（8/8）。

## 5. 验收标准

1. **A**：两条样片核心变色率 ≤ 10%（`w=5`）；单格平均色数 ≤ 3.5；帧数与画布尺寸不变；`pixcli diff` 在 `--temporal 0` 下与改前**逐像素零差异**（保证可回滚）。
2. **B**：读数与离线脚本一致；调大 `w` 时读数单调下降。
3. **C**：`pixcli atlas` exit 0；Unity / Godot 各导入一次无偏移（人工验证一次即可）。

### 实测结果（2026-09-08 落地后）

口径：12fps / 50 帧 / 64×64 / 16 色，样片 = `samples/dog/video/dog_walk.mp4`（绿幕）与 `samples/character/pixel_walk/Pixel_art_walking_animation_202609080040.mp4`（蓝幕）。

| 项 | 结论 | 证据 |
|---|---|---|
| A 零差异 | ✅ 通过 | `--temporal 0` 与改前逐像素零差异（绿幕 / 蓝幕 / 描边三组 `pixcli diff` 一致） |
| A 帧数/画布 | ✅ 通过 | 50 帧、64×64 不变 |
| A 色数 ≤3.5 | ✅ 通过 | dog 3.89→2.93、blue 3.45→2.62（`w=5`） |
| A 核心变色率 ≤10% | ⚠️ **未达标** | dog 31.9%→10.4%、blue 28.8%→13.7%（`w=5`） |
| B 读数一致 | ✅ 通过 | JS `computeStability` 与 `stability.py` 在同一合成帧上**误差 0**；时间维输出逐字节一致 |
| B 单调下降 | ❌ **被推翻** | dog w=0/3/5/7/9/11/13/15 → 31.9/19.8/10.4/13.7/12.2/5.7/9.8/9.1；blue → 28.8/20.1/13.7/11.1/9.2/9.4/8.3/5.2 |
| C `pixcli atlas` | ✅ 通过 | exit 0（含 `--frames` 逐帧逐像素）；负例（重叠/trim/pivot 缺失/tags 断裂）全部拦下 |
| C 引擎导入 | ⏳ 未做 | 需 Unity / Godot 各导一次（人工） |

**「单调下降」为什么被推翻**：中值滤波的取值取决于窗口内多数色峰，窗口跨过不同色峰时结果会跳变——把静态格集合固定在基线（排除「新纳入的高方差边缘格」这一解释）后仍非单调（dog 31.9/19.6/9.5/12.8/11.2/7.8），故这是算法性质而非度量假象。单格平均色数则近似单调（3.89→2.39），是更稳的调参信号。

**拖影实测（2026-09-08 追加，固定 16 色调色板 + dog_walk 50 帧 / 12fps / 64×64）**

「残影」= 输出帧在该像素上显示的是**过去帧**的颜色（与不滤波的当前真值不同）：

| 配置 | 残影 1 帧 | 残影 2 帧 | 稳定性读数 |
|---|---|---|---|
| 时间维 = 0 | 0.00% | 0.00% | 31.9% \| 色 3.89 |
| 时间维 = 3（**新默认**，容差门） | 2.23% | 0.07% | 26.3% \| 色 3.77 |
| 时间维 = 3（旧：精确门） | 4.69% | 0.17% | 19.0% \| 色 3.36 |
| 时间维 = 5（旧默认，精确门） | 5.14% | **2.70%** | 9.0% \| 色 2.59 |
| 后处理·时间稳定 = 3 帧众数（时间维 0） | **1.66%** | **0.00%** | 24.4% \| 色 3.93 |

**结论与最终默认（2026-09-08）**：旧默认 `w=5` 的「稳定 10.4%」是靠**时间冻结**换来的
（2 帧残影 2.70% = 肉眼可见拖影）。最终默认改为 **时间众数稳定 3 帧**（`--stabilize 3`，
时间维 `--temporal 0`）：残影 1 帧 1.66% / 2 帧 **0.00%**，稳定读数 24.4%（CLI 两样片实测
dog 24.6%、blue 21.4%）。众数只在当前帧是窗口内少数派时才替换，且取的是真实色板色，
不像中值那样把 ±2 帧颜色平均进来——**它在闪烁与拖影两个维度同时优于中值**。

**读数警告**：稳定性读数**奖励时间冻结**（压得越狠读数越低、拖影越重），单独看会误导；
`pixcli stability --preset quick` 阈值已由 15% 提到 30%（低拖影配置天然在 25% 上下）。

**§1 门禁的定位**：≤5% 在 `w≤15` 内仅 dog_walk `w=11`（5.7%）接近，两条样片都过不了；因此 `pixcli stability` 的默认阈值定位为**回归探测器**（拦住「改坏了」），而不是「素材合格线」，阈值按素材用 `--max-flip` / `--max-colors` 调。

## 6. 未决 / 不解决

- **网格相位漂移**：`detect_grid` 帧间不稳（`cell` 在 `(7,7)/(7,8)` 或 `(2,3)/(8,6)/(8,7)` 间跳，`conf` 0.64~0.83），说明源视频**没有稳定的逻辑网格**。**2026-09-08 部分回应**：`video-studio.html` 合入可选的**原生网格检测与重采样**（`feat/video-studio-postprocess`）——分析阶段逐帧累积梯度剖面 → radix-2 FFT 功率谱 → 跨帧平均谱找两轴共峰定周期（谱不含相位，不受逐帧相位抖动影响）→ 逐帧梳状搜索取相位圆均值；峰/中位 < 10 或相位一致性 < 0.35 判为无稳定网格并回退常规降采样。实测本源（约 3.47px 网格）可检出并按格采样；对**确无稳定网格**的源仍回退，故本议题对「无网格源」仍成立。
- **素材侧**：高清输入不解决闪烁；素材侧有效的是**大色块平涂风格**（2026-09-09 补记），见 `像素视频-高清素材路线评估.md §7`。
- **产品侧**：画布档位 / 朝向集 / 动作清单归项目 `AGENTS.md`。

原型算法（离线验证用，15 行）：

```python
def temporal_median(maps, pal, w=5):
    """maps: 每帧的 {格坐标: rgb}；pal: 色板 [(r,g,b)]。"""
    n = len(maps); out = []
    for i in range(n):
        lo, hi = max(0, i - w // 2), min(n, i + w // 2 + 1)
        m = {}
        for c in maps[i]:
            seq = [maps[j][c] for j in range(lo, hi) if c in maps[j]]
            med = tuple(sorted(s[k] for s in seq)[len(seq) // 2] for k in range(3))
            m[c] = min(pal, key=lambda p: sum((p[k] - med[k]) ** 2 for k in range(3)))
        out.append(m)
    return out
```

注：原型用 RGB 平方距离选色；**正式实现改用仓库既有的 OKLab 距离**（`standardize.map_with_palette`），保持与全链路一致。

## 8. 未采纳路线附录（原《像素视频-动作稳定性方案》讨论稿）

> 来源：`像素视频-动作稳定性方案.md`（2026-09-07 讨论稿，**2026-09-08 整理时并入本文，原文件删除**）。
> 该讨论稿提出的三条路线**均未实施**——先落地的是本文 §2 的时间维滤波（最小手段、当天可验）。本节只保留根因判断与路线对比，供日后动作幅度问题需要升级时取用。

### 8.1 根因判断（仍然成立）

管线本质是**逐帧独立重采样**：输出像素格在源帧上的覆盖位置随角色运动连续变化 → 同一身体部位被不同源像素混合 → 均值颜色逐帧滑动 → 量化到全局色板后在相邻条目间跳变 → 闪烁与边缘爬行。

- **像素化的视频**：颜色绑定在**空间采样格**上，格随运动漂移，颜色就漂移——稳定性是统计近似
- **像素动画**：颜色绑定在**身体部位**上，动画只是形象在动——稳定性是结构保证

因此本文 §2 的时间维滤波只压**静止区域**的抖动（实测 10.4% / 13.7%），运动区域的漂移与边缘爬行它不解决；A/B/C 是解决运动区域的三条升级路线。

### 8.2 三条路线与对比

| 维度 | A 模板锁帧 | B 部件追踪 | C 姿态驱动骨架 |
|---|---|---|---|
| 核心思想 | 关键帧定型模板，其他帧参照模板生成（A-1 栅格相位锚定：网格钉在角色坐标系、锚定偏移量化到输出格粒度防台阶抖动；A-2 光流搬运：模板像素按流场搬运、颜色直接继承；多模板插值 = 原画+中间画） | 把角色拆成部件（头/躯干/四肢），每部件独立按模板采样、颜色绑死部件后组装（分割：手绘掩码 / SAM2·Cutie·XMem / 姿态分区） | 彻底跳出「视频→像素」：视频只提动作（MediaPipe 骨骼点），像素角色画成分层骨架，姿态数据驱动 rotSprite 播放 |
| 工作量 | 小（A-1 当日可验） | 大 | 最大（动画项目级） |
| 抗大幅动作 | 差（仅平移型） | 强 | 强 |
| 颜色恒定保证 | 继承模板，统计级 | 部件级锁定 | **结构性保证**（颜色从未被重采样） |
| 产出形态 | 序列帧/GIF | 序列帧/GIF | 分层 sprite + 动作数据（可编辑、可进引擎） |
| 技术风险 | 低 | 分割质量决定成败 | rotSprite 失真、姿态映射校准（卡通比例打折） |

### 8.3 选择路径与触发条件

**建议路径**（未变）：先用 A-1 验「颜色恒定是否就是目标观感」→ 动作幅度大扛不住则升级 B → 若终极目标是可编辑资产/进游戏，直接奔 C。

**触发条件**：当采样路线（`video-studio.html` / `pixcli video-std` + 时间维滤波）在动作幅度大的素材上观感不可接受时，按 A → B → C 的顺序取用；单纯「换个更高清的源」不解决（见 `像素视频-高清素材路线评估.md`）。
